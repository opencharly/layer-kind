# 2026.269.0655 — kind: require the kubernetes client candy (kubectl+helm)

## Summary

The first change to land on `opencharly/layer-kind` after its `main` was bootstrapped
via the sanctioned `bootstrap-repo-main.yml` workflow. `layer-kind` is the standalone
home of the `kind` (Kubernetes-in-Docker) candy: the pinned, sha256-verified `kind`
release binary plus a `kind-engine-prepare` script that applies the per-engine host
preconditions for kind's node containers (docker / rootless podman / rootless nerdctl).
Engine selection is charly's own engine word, mapped 1:1 to kind's
`KIND_EXPERIMENTAL_PROVIDER`.

Two changes, both from executing the candy's own plan on a fresh build:

1. **`require: '@github.com/opencharly/layer-kubernetes:v2026.241.0654'`** — the plan's
   stated intent (`plan/kind-integration.md` §4 Phase 1: *"`require:` the existing
   `kubernetes` candy (`layer-kubernetes`, which ships `kubectl`+`helm`) so the client
   toolchain is always present"*) was missing from the manifest, yet the candy's plan
   checks `kubectl version --client`. A standalone `from: kind` compose therefore had no
   declared source for the client toolchain its own plan asserts. The `require:` pulls
   the merged, tagged `layer-kubernetes` candy (kubectl + helm + k3d).

2. **`grep -q` → `grep` in the node-image check** — a latent defect found by *executing*
   the candy's plan (`charly check box` on a fresh build): the check asserted
   `stdout: contains: <digest>` but invoked `grep -q`, which prints nothing, so the
   check could **never** pass. Captured in the first execution below
   (`FAIL … (got: )`) and fixed by dropping `-q` so the matched line is emitted.

Diff: one file, `charly.yml`, **+3/−1** (`+2` for the `require:` block, `−1/+1` for the
`grep` command).

`kind:kindcluster` template kind, its `deploy:kindcluster` provider, its `kind_cluster`
egress schema, and its live R10 bed have already landed (spec, plugin-substrate,
plugin-kube, plugin-egress, charly) and `charly check run check-kindcluster` passes live.
