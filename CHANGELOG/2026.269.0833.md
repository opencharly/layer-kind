# 2026.269.0833 — docs(kind): make layer-kind the canonical owner of the kind skill

## Summary of changes

Make `layer-kind` the canonical **owner** of the `kind` skill (family
`kubernetes`), and fold in the full `kindcluster`-substrate documentation so the
skill lives with the candy it documents.

The `kind` skill currently exists as a `skill:` entity on `candy/plugin-kube`
(merged in plugin-kube#7, to unblock Phase 9 while `layer-kind`'s `main` was
awaiting bootstrap). Now that `layer-kind` is a proper org member, the skill
belongs on the candy's own repo. Regenerating the marketplace with BOTH entities
would collide on one corpus path (`kubernetes/skills/kind/SKILL.md`), so this PR
enriches layer-kind's entity and the companion PR removes plugin-kube's duplicate.

| File | Change |
|---|---|
| `charly.yml` | the `kind-skill:` entity's `content:` gains the `kindcluster:` substrate section (template/deploy authoring, engine-agnostic image load, engine-scoped teardown, the `standard` StorageClass) |

The skill now documents, end to end: the pinned, sha256-verified `kind` binary +
`kind-engine-prepare` per-engine preconditions; engine selection via charly's own
engine word mapped 1:1 to `KIND_EXPERIMENTAL_PROVIDER`; authoring a `kindcluster:`
template + optional-workload deploy; probing with `kube:` (nodes / wait-nodes /
pods / wait-ready / storageclass / raw) and why `kube: addons` is k3s-only (kind
ships kindnet, no Traefik/ServiceLB); the engine-agnostic `kind load image-archive`
path (`load docker-image` is broken on podman); and `kind delete cluster` teardown.

This is Phase 9 of the kind-integration cutover, re-homed to the skill's proper
owner. The companion change (`opencharly/plugin-kube`) removes the duplicate.
